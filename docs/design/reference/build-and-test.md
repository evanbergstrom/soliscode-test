# Build and test

How to build and test, what each gate is here, and what the build does not have yet. All commands run from the repository root. Each part is marked **Built**, **Partly built** or **Designed**, with the task that builds it.

The gates, their switches and the flags never to use are soliscode-parent's, and every child inherits them: [soliscode-parent's build-and-test.md](https://gitlab.com/soliscode/soliscode-parent/-/blob/main/docs/design/reference/build-and-test.md) defines them, and "What a child adds" there says what a child must add. This document says what this project adds and how the gates stand here. Related: [java-conventions.md](java-conventions.md), [dependency-management.md](dependency-management.md).

## Prerequisites

- Maven 3.9 or later.
- Built (#9): JDK 25 on the `PATH`, with no toolchains entry. No preview feature is used. The enforcer refuses an older JDK or Maven.
- `com.soliscode:soliscode-parent:0.1.17` in `~/.m2` (#79; 0.1.14 from #73, 0.1.13 from #71, 0.1.12 from #69, 0.1.9 from #64, 0.1.8 from #57). The POM names it with an empty `<relativePath/>`, so Maven never looks for it in a sibling directory; it is not on Maven Central. A release of soliscode-parent, made in its own clone, installs it, with `com.soliscode:soliscode-performance-api` at the same version, which the performance library depends on (#69).
- Never print or change `~/.m2/settings.xml`. It holds credentials, and Maven reads it without being told to.

## Commands

```bash
scripts/verify.sh                                # the full verify from clean, recorded for releases (#11)
mvn -B clean verify                              # the same build, unrecorded: every gate, the default test selection
mvn -B verify -Pall-tests                        # every test, the extremely-slow ones included
mvn -B test -Dtest='Class#method'                # one test
mvn -B test -Dgroups=concurrency                 # only the tests with a tag (a JUnit tag expression)
mvn -B test -DexcludedGroups=very-slow           # skip other tags instead of the default's
mvn -B install                                   # install 0.1-SNAPSHOT into ~/.m2
mvn -B dependency:analyze                        # libraries used but not declared, or declared but not used
scripts/install-git-hooks.sh                     # once per clone (#11)
```

**Never run two Maven builds at once.** They share `target/` and `~/.m2`.

Built (#10): Checkstyle runs at `validate` and passes, with no finding. It had 2,958 under soliscode-parent 0.1.2 on 2026-11-08 (1,742 in main code, 1,216 in tests), #14. Deactivating its profiles (`-P '!checkstyle-main,!checkstyle-test'`) is on the parent's list of flags never to use, so it needs the user's approval in the current session.

## Gates

Every gate is inherited from soliscode-parent 0.1.17 (#14, #57, #64, #69, #71, #73, #79). This project configures none of them itself. Since 0.1.4 the parent's gate guard refuses a gate plugin's version, dependencies or deciding settings set in this POM, a property that narrows a gate, in the POM or as a `-D`, and a setting the parent fixes given twice in a gate's execution; some flags on `CLAUDE.md`'s list it lets through (`-DskipTests`, `-Dmaven.test.skip.exec` and `-Djacoco.skip` in a verify, `-Djacoco.minimum.coverage`, a gate's profile turned off, `-Dmaven.test.skip`, `-Dmaven.test.failure.ignore`; `-Djacoco.haltOnFailure=false` changes nothing, the check sets it literally); the list holds either way. A profile turned off turns off that gate's guard with it, and a lower `jacoco.minimum.coverage` in the POM passes it. ## Tests

Built (#9). 8,979 tests on 2026-11-14 in the default build, and every one passes. The parent's Surefire runs the classes named `**/*Test.java` and no others, and JUnit runs no abstract class: a test class ends in `Test`, an abstract base ends in `Test` and begins with `Abstract`, and a helper does not end in `Test`.

### Test tags

Built (#5). The annotations in `com.soliscode.test.annotations` add JUnit tags (the names are `TestTags`' constants). Surefire skips the tags in the `excludedGroups` property; `-Pall-tests` clears it, and `-DexcludedGroups=...` replaces it.

| Annotation | Tag | Meaning | Default build |
| :--- | :--- | :--- | :--- |
| `@Slow` | `slow` | 100 ms – 1 s | runs |
| `@VerySlow` | `very-slow` | 1 s – 10 s | runs |
| `@ExtremelySlow` | `extremely-slow` | over 10 s | **skipped** (`-Pall-tests` runs it) |
| `@ConcurrencyTest` | `concurrency`, `nondeterministic` | thread-safety test, repeated (`THREAD_SAFETY_REPEATS`, 5), with a timeout (`THREAD_SAFETY_TIMEOUT`, 10 s) | runs |
| `@Nondeterministic` | `nondeterministic` | may pass or fail differently between runs | runs |

The default was chosen by the user on #5 (2026-11-07), so that the thread-safety contracts run on every build. No test is tagged `extremely-slow` yet.

**Time.** The default `mvn clean verify` took 5:10 min on 2026-11-15, for 9,297 tests (18 cores, load average 3–8, JDK 25), with `ExecutorServiceContract` (#45), whose breaks that wait out a 5 s bounded call add about 45 s; it took about 4¼ minutes on 2026-11-14, for 8,979 tests (load average about 2); it took about 2½ minutes on 2026-11-08, for 6,230. The tests alone took about 3:54 without coverage (4:32 on `main` before #12, whose corrected yield saves about 40 s), the thread-safety part of `ContractCoverageTest` (`very-slow`) about 70 s of it. The untagged tests (`-DexcludedGroups=slow,very-slow,extremely-slow,concurrency,nondeterministic`) took about 2:20, almost all of it the rest of `ContractCoverageTest` (136 s), which has grown with each contract since 13 s on 2026-11-07. Measure test time with `-Djacoco.skip=true`, since the coverage agent slows the tests; never in a full verify.

### Contract coverage

Built (#6). `ContractCoverageTest` (`src/test/.../contract/coverage`) shows that each contract can pass and can fail. For each contract it runs every test method against a JDK implementation and against an unbroken breakable implementation, which must pass, and then against the breakable with each of its breaks, one at a time, through the breakable's builder (or, for a breakable with none, its constructor, in the coverage test's subjects), which must fail. A break that shows only when a method is unsupported, or when incompatible types are refused, is applied with that configuration too.

- The contracts it covers: `ObjectContract` (#70), `IterableContract`, `IteratorContract`, `ListIteratorContract` (#37), `WeaklyConsistentIteratorContract` (#55), `SpliteratorContract`, `SpliteratorOfIntContract`, `SpliteratorOfLongContract`, `SpliteratorOfDoubleContract` (#38), `MapEntryContract` (#39), `ComparableContract` (#40), `AutoCloseableContract` and `CloseableContract` (#41), `ComparatorContract` (#42), `CharSequenceContract` (#43), `FutureContract` (#44), `ExecutorServiceContract` (#45), `LockContract` and `ReadWriteLockContract` (#46), `CollectionContract`, `SequencedCollectionContract`, `ListContract`, `SetContract`, `SequencedSetContract`, `SortedSetContract`, `NavigableSetContract`, `QueueContract`, `DequeContract`, `BlockingQueueContract`, `BlockingDequeContract`, `TransferQueueContract`, `MapContract`, `SequencedMapContract`, `SortedMapContract`, `NavigableMapContract`, `ConcurrentMapContract`, `ConcurrentNavigableMapContract`, `ThreadSafeCollectionContract`, `ThreadSafeSequencedCollectionContract` (#22), `ThreadSafeBlockingQueueContract`, `ThreadSafeBlockingDequeContract`, `ThreadSafeTransferQueueContract`, `ThreadSafeConcurrentMapContract`, `ThreadSafeFutureContract` (#44), `ThreadSafeExecutorServiceContract` (#45), `ThreadSafeLockContract` and `ThreadSafeReadWriteLockContract` (#46) and `SerializableContract`. `IntegerContract` is not in it.

The map runs take these three alone of `BreakableIterator`'s breaks. `WeaklyConsistentIteratorContract` passes against the iterators of `ConcurrentLinkedQueue`, `ConcurrentHashMap.newKeySet()`, `ConcurrentSkipListSet`, `CopyOnWriteArrayList`, `LinkedBlockingQueue` and a full `ArrayBlockingQueue`, fails against `ArrayList`'s (fail-fast), and fails for each of `BreakableIterator`'s breaks on a breakable over a `ConcurrentLinkedQueue`'s iterator.
- A break it leaves out is one that is not a fault for that contract's type, or that no test could reliably see. `UncheckedReasons` (in the test sources, beside `ContractCoverageTest`) gives the reason for each, one rule method per kind of break; a new exclusion goes into the rule method of its kind, or a new one, with its reason (#65).

A new contract or breakable is added to it, so that every break is shown to fail some test.

### Bounds

Built. Concurrency and deadlock tests do not sleep and do not wait without a limit. `ContentionCoordinator` gives its workers a start and a finish timeout (5 s each by default). It stops waiting for workers that outlive the finish timeout, checks for a deadlock, and interrupts them; its threads are daemon threads, so a deadlock fails the test instead of hanging the build. `@ConcurrencyTest` adds a JUnit timeout. The workers yield before their first iteration and then once every `yieldInterval` iterations (#12); before #12 they yielded on half the iterations, in runs of `yieldInterval`, which slowed the contention runs under load enough to time them out. With a phase interval (#54), a worker waits, after each interval of its calls that has a call after it, until every worker still running has made as many: it spins while the machine has more cores than workers still registered, so that the workers on a CPU start each phase together, and yields otherwise, so as not to keep the awaited worker off its core. A worker leaves the phases once it has no arrival left (after its last, or before its first call if it has no more calls than the interval), and when it throws; the phaser is terminated on every early end of a run (a timeout, an interrupted test thread, before each `shutdownNow`), and by a worker interrupted while it waits. No call may wait for another worker's progress beyond the current phase: the put/take tests keep each phase balanced (as many puts as takes, so a `take` that blocks has a `put` of its phase still to come). Under 18 busy processes, the phased map tests' passing runs took at most 2.2 s (`replaceThreeArg`, 200 phases); the phased queue tests' at most 1.9 s (`putAndTake` on the fair store), against 5 s; the transfer tests on the fair store ran into their budget, at most 6.04 s against 9 s. With the JVM told it has 2 cores (`-XX:ActiveProcessorCount=2`, so that the waits yield and the thread counts are a 2-core machine's; not a CPU limit: no container could be used), idle every map break was caught 20 of 20 and passing runs took at most 46 ms; under 18 busy processes passing runs took at most 0.3 s, and some breaks were caught less often than with 18 cores (map `FOR_EACH_IS_NOT_THREAD_SAFE` 14 of 20, deque `POLL_FIRST_WITH_TIMEOUT_IS_NOT_THREAD_SAFE` 17, `PUT_IF_ABSENT`, `GET_OR_DEFAULT` and the queue's `POLL` 19, the rest 20).

## Releases

The version is `${revision}`, `0.1-SNAPSHOT` on `main`; releases are `0.1.N`, installed in the local Maven repository only, and the parent's flatten plugin writes the installed POM with the version resolved. ### The record of a green build

Built (#11), as in soliscode-quant. `scripts/verify.sh` takes no arguments. It refuses to run if `MAVEN_ARGS` is set, since Maven would add it to the build, or if `MAVEN_OPTS`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS` or `JDK_JAVA_OPTIONS` sets a property, which the JVM would pass to Maven; `release.sh` refuses the same. It runs the full verify from clean, `mvn -B clean verify`, with its log in `$(git rev-parse --git-common-dir)/soliscode/verify.log` (outside `target/`, which the `clean` deletes), and, if the build is green, records it:
- **Key:** the tree of the working copy when the build started: every tracked file, and every untracked file `.gitignore` does not exclude. The script names it with `git write-tree` from a temporary index (`git read-tree HEAD`, then `git add -A`), so the real index is not touched.
- **Where:** `$(git rev-parse --git-common-dir)/soliscode/verified/<tree>`, inside `.git`: local to the clone, shared by its worktrees, never committed.
- **What:** the date, the commit `HEAD` was at, and the test totals from Surefire's reports.
- A build is recorded only if it ran tests, none failed or errored, and the coverage check was met once and not skipped (`All coverage checks have been met.` in the log, no `Skipping JaCoCo execution`).
- If the tree changed while the build ran, nothing is recorded, and the script says so.

A branch's green verify counts for its squash merge on `main` when the merge's tree is the branch's working copy. Otherwise there is no record for the merge (never a wrong one), and the `release` skill runs the verify once on `main`.

Built (#10): with Checkstyle passing, the full verify runs to the end, and `verify.sh` records it. Before #10 it failed at `validate`, so its other steps were tested with Maven replaced by a stub (#11's notes).

### `release.sh`

Built (#11). `scripts/release/release.sh --changes <file> [--trailer <line>]...`. `<file>` holds the release's changes as bullets, in the entry format's style, without a heading; the script adds `### Changes`, and refuses a file with a heading line. It runs with `set -euo pipefail`:
1. Refuses unless it runs on `main` with a clean working copy (`git status --porcelain` empty), and `<file>` exists and is not empty.
2. Finds the version: `0.1.N`, one past the highest tag of the form `v0.1.<digits>`, or `0.1.1` if there is none. Refuses if `v0.1.N` exists.
3. Refuses unless a record of a green build exists for `HEAD`'s tree, and says to run `scripts/verify.sh`.
4. Builds and installs the release from clean, `mvn -B -Drevision=0.1.N -DskipTests -Djacoco.check.skip=true clean install`: the record shows the tests green for this tree.
5. Writes the release's entry to `RELEASES.md`: the version and date, `HEAD`'s commit, the test count from the record, the install coordinates, and `### Changes` followed by the contents of `<file>`. The entry takes the place of the `## Unreleased` section's contents (up to the next `## ` heading), and an empty `## Unreleased` stays above it, so the next tasks' changes go there. The line "No release has been made yet." is removed.
6. Commits `RELEASES.md` alone as `Release 0.1.N`, with the `--trailer` lines given, then tags that commit `v0.1.N`, annotated. Nothing is pushed. If writing or committing fails, `RELEASES.md` is restored from `HEAD`.

## Git hooks

Built (#11). `scripts/install-git-hooks.sh` sets `core.hooksPath` to `scripts/git-hooks/`; run it once per clone.
- **pre-commit:** when the staged changes touch `src/`, `pom.xml`, `.mvn/` or `.errorprone`, or `HEAD`'s tree has no record (the first commit after installing, an amended `--no-verify` commit), it compiles the main and test sources (`mvn -B -q -DskipTests -Djacoco.skip=true test-compile`), which runs the enforcer, the licence gate, Checkstyle, ErrorProne and NullAway. It refuses a commit that leaves one of those files unstaged or untracked, since the build would vouch for something the commit lacks. On success it records the staged tree in `$(git rev-parse --git-common-dir)/soliscode/pre-commit/`.
- **pre-push:** refuses a push to `main` of any commit whose tree has no pre-commit record here, such as one made with `--no-verify`.

The hooks start Maven: don't commit while a background build is running. Before #10 made Checkstyle pass, a commit that the pre-commit hook built failed at `validate`, so the hooks were not installed in this clone; they are installed once #10 is merged (#11's notes).

## The published Javadoc

Built (#77), from soliscode-parent 0.1.17's template set (the revision in `docs/.doc-templates-version`; its design is the parent's `docs/design/reference/documentation.md`, section 3). Each release's Javadoc from 0.1.6 on (the release current when #77 merged; 0.1.1 to 0.1.5 are not published) is on the project's GitLab Pages site, once the first publish below has run, `https://soliscode.gitlab.io/soliscode-test/<version>/`, the newest also at `/latest/`, and `/` lists the versions.
- **`scripts/publish-javadoc.sh <version>`**, the parent's, unchanged. It builds the release's site in a worktree of the tag `v<version>` (`mvn -B -Drevision=<version> -DskipTests -Dmaven.test.skip.exec=true package site`, which runs no test, since parent 0.1.15), so the working copy is not touched; stores `apidocs/` as the generic package `javadoc/<version>/javadoc.zip`, unless that version is stored already (a tag does not change); starts a pipeline on the project's default branch, `main` (since parent 0.1.16), with every stored version as its input; runs this machine's project runner for that one job; and checks the site over HTTP, without credentials. `--check <version>` prints the project's settings, the runner's readiness and who can read the site, and changes nothing; `--store-only <version>` stores without starting a pipeline; `--register-runner` registers the runner, once per machine and project. It refuses a site or registry readable more widely than the source, so this project is public (the user's decision on #77, 2026-11-23): the script checks three surfaces, all set for everyone (visibility `public`, and the repository, Pages and package registry `enabled`, which on a public project is everyone; `--check` reads them). The project's other features are set apart from these: today issues, merge requests, the wiki, snippets, the container registry and CI/CD are `enabled`, with `public_jobs` on, so they and the job logs are readable by everyone too. It can be cloned over HTTPS without membership; the guide pages that said it was private (`docs/user-guide/getting-started/installation.md`, `docs/developer-guide/contributing/workflow.md`, `docs/developer-guide/getting-started/dev-environment.md`) no longer do. It refuses a runner paused in GitLab, and gives up on a Pages site that does not answer (since parent 0.1.17). While it runs, no other Maven build runs and nothing is committed (the git hooks start Maven).
- **`.gitlab-ci.yml`**, the parent's, unchanged: the one pipeline. It runs only when started through the API (no push, merge request or schedule starts one), and its one job, `pages`, tagged `soliscode-pages` so that only a publisher's project runner takes it, on a pinned `alpine` image (dependency-management.md), downloads each stored version and unzips it into the site. It builds nothing and runs no gate. GitLab reads it from `main`, so a publish runs only once `main` has it. Check a change with `glab ci lint`.
- **Settings, set once** (each the user's to approve): the project public, Pages `enabled` (everyone, on a public project), the unique domain off, so that the address is `https://soliscode.gitlab.io/soliscode-test/`, and a project runner on each publisher's Mac (`brew install gitlab-runner`, Docker running, `scripts/publish-javadoc.sh --register-runner`). The developer guide's [CI and the Javadoc site](../../developer-guide/maintainers/ci-cd.md) has the detail.
- **In a release**, the `release` skill pushes `main` after `release.sh` (`git push origin main`), then runs `scripts/publish-javadoc.sh 0.1.N` in the background, telling the user it builds the site at the tag without running the tests, and holds off other builds and commits. If the push fails (origin has moved on, so the release was made on a stale `main`), the skill stops before the publish and reports it: the release is local and stands, and the user decides how `main` is reconciled. The publish runs only once `main` is pushed, so the site never shows a release whose `RELEASES.md` entry GitLab lacks. A failed publish does not undo the release: the tag and the installed artifacts stand. It is reported, and the script run again, which skips a stored version. The tag need not be pushed: the script builds from the local tag.
- **One publisher at a time** (the parent's stated limit, documentation.md, section 3.2). The script reads the stored versions before it checks for a running pipeline, so two maintainers publishing at once could deploy an older list after a newer one, taking the newer version off the site. Publish from one place at a time. The script's last check, with the site readable by everyone, compares the deployed `versions.txt` with the registry and fails on a mismatch: then run it again, which skips the stored version and redeploys every stored one.
- **The first publish** is after #77's merge, since a push starts no pipeline and GitLab's `main` needs `.gitlab-ci.yml` first: `scripts/publish-javadoc.sh 0.1.6`, the release current then. `v0.1.6` builds on parent 0.1.12, so soliscode-parent's 0.1.12 release (the parent, its build tools, its plugins and the performance API) must be in the local Maven repository (they are, from that release). The script's own checks, over HTTP without credentials, show the site: `/0.1.6/`, `/latest/` and `/latest/VERSION`, and `versions.txt` against the registry. Their result goes on #77. Until then the site is empty; the settings, the runner and the files above are Built before the merge, and the published site is Built with that result.
